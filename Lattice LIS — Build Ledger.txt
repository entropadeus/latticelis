### New modules

- **`rules-runtime.js`** — `*` event subscriber with **serialized** queue (eliminates rule.stats race). 25+ condition primitives implemented (incl. real `result.delta.gt` with prior-result lookup), 17+ action executors, ctx refresh between actions in same rule. Action `order.reflex.add` publishes `order.updated` so the simulator hears reflex changes.
- **`lifecycle.js`** — central completion watcher. Specimen-completion is owned by writers (simulator, accessioning); the watcher's single responsibility is order-completion = `all specimens terminal AND all results final/corrected/cancelled`. Subscribes to 4 triggers: `result.verified`, `result.released`, `specimen.completed`, `specimen.rejected`. Exports `canTransition`, transition graphs, `specimenHasAllResults`, `isOrderComplete`.
- **`instrument-sim.js`** — listens to `specimen.routed` AND `order.updated`. Order-aware: re-derives pending tests at fire time so reflex tests added during the sim delay are emitted in the same run. Emits `specimen.completed` after writing terminal state.
- **`current-user.js`** — auto-seeds 2 operators (Alex Tran / Morgan Lee), persists selection in localStorage, exposes `window.currentUser` + `window.currentUserApi.displayName(actor)` for human-readable actor lookup. Synchronous `__userCache` keeps tight rendering loops fast.
- **`entity-drawer.jsx`** — universal slide-in detail drawer. Globally openable via `window.openEntity(kind, id)`. Three tabs: Overview (kind-specific facts + linked neighbors), Timeline (audit_events filtered by entityId), Related (graph neighbors). Renders specimen/order/patient/result.
- **`critical-alerts.jsx`** — sticky top-right banner stack for unacked criticals. `criticalAckedAt`/`criticalAckedBy` persisted on the result so reloads don't drop alerts. Per-result Acknowledge + global "Ack all" + collapse.

### Polish session - 2026-05-12 (local) - Accessioning fixes: label modal, session persistence, clear session, patient typeahead

**Tackled:** Four issues surfaced by the user in one pass on the Accessioning page. (1) Clicking the row-level **Label** button opened the modal but it appeared blank/broken. (2) The action-row **Print label** button was a dead element (no `onClick`) and the **⌘L** shortcut was a documented no-op (`// real wiring would print`) — pressing them did nothing. (3) Accessioned specimens vanished from the Session log when the operator navigated away (e.g. to Dashboard) and returned. (4) Operator wanted a typeahead on **Patient / MRN** so existing patients surface as they type instead of being stubbed as fresh records by `resolvePatient` on every commit. Operator also asked for an explicit **Clear session** control to reset the log between batches without dropping the underlying specimens.

**Root causes (in the order they bit):**

1. **`labels.js` meta units bug.** `build()` returned `meta: { width: usedTemplate ? (template.width || W) : W }` where `W = 203` is *dots*, but `renderHtml` multiplies meta dimensions by `SCREEN_PX_PER_INCH (144)` because everywhere else in the codebase `meta.width/height` are *inches* (template editor saves `2.0`, etc.). When no template matched (the seed case), `widthIn = 203` → `pxW = 29,232`. The preview div rendered at 29232×58464 px inside a `gridTemplateColumns: '320px 1fr'` column wrapped in `overflow: hidden` — so the modal's left half clipped to 320px of an enormous off-screen label, which read as "blank." The ZPL was correct the whole time; only the HTML preview path was broken.
2. **Action-row `Print label` had no handler.** Comment-confirmed stub: `<button className="btn" data-size="sm">Print label</button>` + ⌘L handler `if (meta && key==='l') { e.preventDefault(); return; }`. Literal dead controls.
3. **`sessionStart` reset on every mount.** `const [sessionStart] = useStateAC(Date.now())` initialized on each component lifecycle, and the session log filters `s.createdAt >= sessionStart`. ### Agent session — 2026-05-07 (late evening, local) — Instrument simulator: catch-up scan + completion-on-noop fix

**Tackled:** User reported "the simulated instrument not running my tests." Inspecting their state revealed two compounding problems: (1) their hand-created specimen was at `state: 'in_analysis'` with `routedTo: null` and zero audit events — never went through the canonical route flow, so `specimen.routed` never fired and the simulator never heard about it; (2) even if it HAD been routed earlier, the simulator is purely event-driven, so a page reload would have orphaned the in-flight work anyway. The simulator had no way to recover from either scenario.

**Produced:**

1. **`maybeCompleteSpecimen(specimenId)` helper** (`instrument-sim.js`) — extracted the "all results in → transition `in_analysis → completed` + publish `specimen.completed`" logic into a shared function. Both the result-generation timer AND the catch-up early-exit now go through it, so there's one source of truth for the completion rule.

2. **`runSpecimenWork` no longer early-exits on no-pending-tests without checking completion.** The previous `if (pendingTestIds.length === 0) return;` was the precise bug: if a specimen sat at `in_analysis` with all results already in (post-reload, manual db edit, snapshot import), the simulator would return without checking whether the spec should advance to `completed`. Now it calls `maybeCompleteSpecimen` before returning, so stuck specs get rescued.

3. **`catchUp(sourceLabel)` scan** (`instrument-sim.js`) — new boot-time + on-re-enable scan. Lists every specimen at `state: 'in_analysis'` with an `orderId` and runs `runSpecimenWork` on each. Sequential to keep the db view consistent. Wired in two places:
   - `start()` — runs once at boot (1.5s after start, so the rest of the boot finishes first).
   - `setEnabled(true)` — runs when the operator re-enables the simulator after disabling, so any work queued during the off-window resumes.
   Specimens at `received` are deliberately NOT picked up — those haven't been routed yet, and auto-routing without an instrument target would silently skip the operator's choice. They surface in the Worklists "Unrouted" bucket as before.

4. **"Re-scan in-flight" button** (`other-pages.jsx`) — InstrumentsPage header gains a manual catch-up trigger. Title text explains: "Use after a page reload, after re-enabling the simulator, or to recover a stuck specimen." Lets operators kick a re-scan without waiting for an event-driven trigger.

5. **`window.instrumentSim.catchUp` exposed** so the admin UI button + tests + future rules primitives can invoke it.

**End-to-end verified via Chrome MCP:**

- **Boot catch-up rescues the user's stuck specimen.** On the fresh page load, console showed `[instrument-sim] catch-up scan: 27 specimen(s) in flight`. The user's specific spec (`spec_aowu6pphibp0`, WBC test, `routedTo: null`) transitioned `in_analysis → completed` and the parent order cascaded `open → completed` via the lifecycle watcher — confirmed by reading the audit_events chain: `lifecycle.transition spec→completed` → `specimen.completed` → `lifecycle.transition order→completed`. All 27 stuck demos cleaned up too (`stillInAnalysis: 0` after scan, was 27 before).
- **Live happy path still works.** Created a fresh STAT order + spec, manually routed via `lifecycle.transition` + published `specimen.routed`. ~3 seconds later: `kind: scheduled` then `kind: result` in sim activity buffer (test=K, value=3.62). Spec auto-completed via the result-generation path's `maybeCompleteSpecimen` call. Order stays `open` waiting for `result.verified` — correct; lifecycle gates order completion on result finality, not specimen completion alone.
- **No console errors.**
- **Cache version bump:** `ba` → `bc` (intermediate `bb` was a partial fix that didn't include the no-pending-tests completion-check).

**What I deliberately did NOT do:**

- **Auto-route received specimens to a default instrument.** Tempting — would catch the user's "I made an order but never did anything else" path automatically — but routing without an operator-chosen target silently picks an instrument the lab might not have available. The Worklists "Unrouted" bucket is the correct surface for this; the operator picks an analyzer.
- **Forensic root cause on how the user's specimen got `state: 'in_analysis'` without `routedTo`.** Could be from earlier dev iteration, manual db edit, console paste, or snapshot import. Since the catch-up handles whatever caused it AND we have lifecycle.transition guarding new transitions, a forward-fix beats backward-investigation.
- **Pause-the-clock semantics for catch-up timing.** A specimen rescued via catch-up has its result `resultedAt` stamped at scan time, not the original route time. For TAT analytics that look at instrument-side intervals this is a small skew. Acceptable for a simulator standing in for real ASTM/HL7 transport.

**Decisions:**

- **Catch-up is a separate function, not folded into `runSpecimenWork`.** Two reasons: (a) callers can invoke it directly from the admin UI without needing a specimen id, and (b) the source-label tracking ('boot' vs 're-enable' vs 'manual') stays explicit in the activity log. Folding would mean every per-specimen call writes a "catch-up" log entry that isn't really a catch-up.
- **Boot scan defers 1.5s.** Same rhythm as `tat-watcher` and `lot-expiry-watcher` — gives the toast subscriber + drawer + bell time to wire up before any notification fires. The simulator doesn't currently fire `notification` events, but the pattern is consistent with the rest of the bus.
- **`maybeCompleteSpecimen` is idempotent on already-completed specs.** Returns `false` if state isn't `in_analysis`, so calling it twice is safe — important because the catch-up scan and the result-generation timer both call it on the same spec when work overlaps.

**What I deliberately did NOT do (honest gaps):**

- **Per-priority recipient routing** — today, all roles in `tatRecipients` get every TAT alert regardless of priority. Real labs sometimes route STAT to LAB_DIRECTOR but Routine only to LAB_SUPERVISOR. Modeled as a future schema extension (matrix of priority → roles) rather than built speculatively.
- **TAT clock pause for legitimate hold states** — an order in `cancelled` doesn't accrue TAT (✓ honored: the watcher ignores terminal orders), but a specimen reject + pending re-collect SHOULD pause the clock. Acceptable trade-off; alternative would be a "force re-notify all" admin action.
- **NotificationsPage configurability beyond TAT** — the tile description says "Alerts, escalations, AR notifications" and today only surfaces TAT. Critical-result escalation thresholds still live in Test Catalog (per-test). Delivery-failure escalation lives in `delivery-watcher` (no UI knobs). - **Watcher does not honor `prefers-reduced-motion`-style "quiet hours"** — pages 24/7. Some labs only want TAT alerts during operating hours. Future config under the Notifications page.

**Decisions:**

- **TAT is time-driven so the watcher is a poller, not a subscriber.** Order writes don't change elapsed time; only the wall clock does. A 60s tick is granular enough for the smallest default threshold (60min STAT) — worst case alert is 1 min late. Alternative was a write subscriber with a 60s setTimeout per active order; rejected as N×timer churn.
- **Discovery mode prevents notification flood on cold start.** Without it, the `__demo_` seed (~25 orders past STAT/ASAP threshold) would dump 25+ toasts on first load, drowning real signal. The discriminator (`tatNotifiedLevel === undefined`) is robust because `schema.newOrder` now always initializes the field to `'ok'`; only old/imported records lack it.
- **Storage of TAT state on the order itself, not in a parallel collection.** `tatBreachLevel` lives on the order so every read (Orders page, drawer, dashboard) sees it without a join. The audit_events stream still records every climb for compliance / retrospective analysis. No `tat_breaches` collection — would duplicate state and risk drift.
- **Pure `classify()` exposed as `window.tatWatcher.classify`** so the Dashboard panel, the order drawer's progress block, and any future rules primitive share the same arithmetic. Single source of truth for "is this order breaching?".
- **Recipient list cannot be empty.** A no-recipients config is a misconfig that silently swallows alerts; the toggle no-ops on the last role rather than letting the user reach an unsafe state. Future iteration could replace this with a clearer error toast on save attempt.
- **Threshold inputs accept arbitrary integers; coerce-to-default on bad input.** Negative / zero / NaN / non-numeric all fall back to defaults via the schema factory. Same defensive resolver pattern used by `critical-escalation.resolveThresholds` — defaults-on-misconfig over silent acceptance.
- **`tatBreachedAt` set on the *first* breach transition only, not every breach climb.** A warn → breach → ok → breach sequence captures only the first breach timestamp, but `audit_events` has the full chain for forensic reconstruction. This keeps the "+Xh" pill stable when an order's breach state oscillates.
- **Audit events publish entityType: 'order' + entityId: order.id** so the Activity Log entity click-through wire (shipped 2026-05-07 evening) routes TAT events to the order drawer for free. No bespoke handler needed.

**Cache version:** `ay` → `az`.

- Token resolution: `getComputedStyle(...).getPropertyValue('--ease-out')` returns `cubic-bezier(0.16, 1, 0.3, 1)`. `--dur-base` returns `180ms`.
- Page load: `.fade-in` present on the active page wrapper.
- Dashboard: `.stagger-children` confirmed on the KPI strip, 5 children counted.
- Admin: tile grid renders cleanly with stagger + lift classes.
- Drawer: clicked a Results row, drawer opened — both `.drawer-in` and `.backdrop-in` mounted.
- Console: zero errors, zero warnings.
- Reduced motion: media query clamps all durations to 1ms; verified by reading the stylesheet rule.

**What I deliberately did NOT animate (honest gaps):**
- **Numeric KPI value transitions.** A real LIS gets KPI updates every few seconds; animating a count-up between 22 → 23 would feel theatrical. Kept the snap.
- **Table row fade-in on data load.** With 200+ rows on Results, a cascade would feel laggy and steal focus from the data. Tables paint instantly.
- **Tab underline slide on drawer tab switch.** Would need a layout-shifting indicator (or framer-motion-style shared layout). Not worth the dependency for a 2px line.
- **Notification toast exit animation.** Toasts dismiss instantly on click. A fade-out would queue removal and feel sluggish. Acceptable trade-off.
- **Sidebar collapse/expand transition.** The hybrid layout swap is grid-template change, which CSS can transition but only on numeric grid values. Skipped — rare action, not worth the complexity.

**Decisions:**
- **Out-quint (`cubic-bezier(0.16, 1, 0.3, 1)`) for entries; standard Material easing for state changes.** Out-quint gives a strong initial motion that decelerates sharply — feels expensive without being showy. Material standard for hover/focus is calmer and predictable.
- **180ms is the sweet spot for entries.** Faster (120ms) feels like a snap; slower (240ms+) introduces perceptible lag in a dense workflow tool. Modals get 240ms because the larger surface needs more arc to read as deliberate.
- **No spring physics, no overshoot.** Lab software is precision tooling. A bouncing modal in a CLIA-compliant audit context reads as unserious. Smooth deceleration only.
- **GPU-friendly properties only** — `opacity`, `transform: translateX/translateY/scale`. Never animate `width`/`height`/`top`/`left` (causes layout) or `box-shadow` directly (paint-heavy unless on a single small surface). The `lift` class is the only `box-shadow` transition and it's gated to `:hover` on small tiles.
- **`will-change: transform` only on buttons and `.lift`** — declared sparingly because over-use hurts memory. Buttons warrant it because they're the most-touched surface.
- **Reduced-motion clamp uses 1ms, not 0.** A pure `0` confuses some browsers' state machines; 1ms is functionally instant but keeps the transition state machine alive.
- **Stagger via CSS `:nth-child` not JS state.** No render-time delay calculation, no per-component animation state, no fragility. The stagger is purely declarative and respects reduced-motion automatically through the same media query.

**What I deliberately did NOT verify (honest gaps):**
- **Chain-of-3 end-to-end via UI.** The modal allows correcting a corrected record and the chain panel handles arbitrary depth, but I didn't drive a 3-version chain through the UI. Programmatic round-trip confirmed the data model works at any depth.
- **HL7 OBX-11='C' on the re-delivered wire** — `hl7.buildORU` already maps `result.status === 'corrected'` → `OBX-11: 'C'` (verified by inspecting the existing mapping at `hl7.js:144`), but I didn't grab the framed payload from a corrected delivery to verify the byte. Confidence high; verification not run.
- **Critical-flag re-detection on correction** — if a corrected value crosses a critical threshold the prior didn't, the existing rules-runtime should fire `result.critical` against the new record (because RESULT_RECEIVED is republished). I didn't seed this scenario explicitly.
- **Correcting a result with `criticalAckedAt` set** — the prior's ack stamp doesn't carry over to the corrected record (intentional — the corrected value is a new clinical signal that needs its own ack chain), but the original's ack stays on the prior. Untested for the case where the corrected value is itself critical.
- **Concurrent corrections on the same prior.** Two operators issuing corrections at the same moment would create two siblings both pointing at the same `correctionOf`. Last-write-wins on `supersededByResultId`. Real-world race window is small but real; not handled.
- **`correctionOf` snapshot semantics during snapshot import** — if an export contains a corrected record but its `correctionOf` target was deleted, the chain becomes orphaned. The drawer chain panel walks by `(specimen, test)` membership rather than strictly via `correctionOf`, so it's resilient to this.

**Decisions:**
- **Correction creates a NEW record; prior is NEVER overwritten.** This is the audit-trail religion — the prior really WAS final at the time it was reported (delivered, in some cases). Mutating its status would erase that history. The chain is the audit trail.
- **Corrected record is auto-verified by the issuing operator** rather than going back to status `preliminary`. Real labs treat the correction itself as the verification — the operator who issued it is signing off, no second pair of eyes needed (some labs add that workflow but it's regulator-specific).
- **Auto-release the correction iff the prior was released.** If the prior went out, the client must see the amendment. If the prior was held internally, the corrected record waits for an explicit release (operator may want to verify the corrected value before reporting).
- **Reason dropdown with preset options + free-text comments** rather than a single free-text. Preset reasons are CLIA-trackable categories — labs need to report correction rate by category. Free-text would land everything in "Other".
- **`supersededByResultId` is a stamp, not a status change.** The prior's status stays `final`. Display-time filtering (`!supersededByResultId`) hides it from the latest-only view; explicit toggle reveals the audit trail. This avoids the lifecycle question of "what's the correct status for a superseded final result?" — it's still final, just no longer the current report.
- **Walk by `(specimen, test)` membership for the chain panel, not strictly `correctionOf`** — robust against partially-malformed chains (e.g. a prior session's corrected record without a back-reference). The chronological sort gives the same ordering as a clean linked-list walk in nearly every case.
- **Skip the modal-side "save" guards on numeric format.** `isNaN(Number(draft.value))` is checked at save time but the input doesn't reject non-numeric typing — string results (e.g. "POSITIVE") are valid for some test types. The save path picks numeric vs. string by `isNaN` and applies flag logic only when numeric.

### User session — 2026-05-07 (evening, local) — Manual result entry: depth + drawer remount fix

**Tackled:** Per user direction, the "manual Result Entry form" gap on the Current State table. **Discovery during inspection:** the form was actually already shipped in `entity-drawer.jsx` (`ManualResultEntry` component within `ResultsForSpecimen`). What was actually missing was real lab depth + a pre-existing render-race bug that made the form unreachable from a cold drawer open.

**Bug caught (pre-existing, not introduced this iteration):**
- `ResultsForSpecimen` calls `useEntities('tests', t => order && order.testIds.includes(t.id))`. The filter closure captures `order`, which is null on first render of `SpecimenOverview` (the parent does `useEntity('orders', specimen.orderId)` — async). `useEntities` reload only re-fires on collection writes, NOT on filter-identity changes. Result: when the order finishes loading, the closure has been replaced via `filterRef.current = filter`, but reload doesn't re-run, so `tests` stays at `[]` and `pendingTests` stays at `[]` and the "Enter results manually" button never appears. The drawer always claimed "all tests resulted" even when zero of N tests had results.
- **Fix:** re-key `<ResultsForSpecimen>` on `order.id` so it remounts when the order becomes available. One-line fix; doesn't touch the broader `useEntities` API. Reproduced and verified the fix end-to-end via Chrome MCP.

**Produced (depth additions to existing ManualResultEntry):**
- **Demographic-aware reference range resolution.** The form now calls `referenceRanges.pick(test, { patient, asOf })` per row at mount time, the same way the simulator does. Patient lookup via `useEntity('patients', specimen.patientId)`. Resolved range overlays the test's catalog default when the patient's sex / age / method matches a test-specific range.
- **Range source pill** next to each row's range. Sage `matched` = the patient hit a demographic-specific range (e.g. F-only). Ghost `default` = no demographic match, falling back to the test's catalog-wide range. Visible at-a-glance feedback so the operator knows whether the displayed range is patient-tuned or generic.
- **Ref range snapshot** — `refRangeSource` and `refRangeId` written onto every persisted result, matching what the simulator already does. Audit trail integrity: a result's range is preserved even if the test catalog is later edited.
- **Verify-on-save** per-row checkbox. Checked rows are written with `status: 'final'`, `verifiedBy`, `verifiedAt` set immediately, and publish both `RESULT_RECEIVED` (so reflex / critical-flag / delta rules cascade) AND `RESULT_VERIFIED` (so the lifecycle watcher promotes the order if appropriate). Unchecked rows remain `preliminary` and require a separate verify step. Header counter shows "X of Y filled · Z verify-on-save" so operators see the split before clicking Save.
- **Comments column** — schema's `comments` field is now editable inline (was previously unused in this form). Useful for "Lipemic specimen, repeated" or "Confirmed by manual count" notes.
- `index.html` cache version `20260507aq` → `20260507ar` (form changes) → `20260507as` (drawer remount fix).

**What I deliberately did NOT verify (honest gaps):**
- **Reflex-cascade on manual entry not specifically tested.** A rule like "if HGB < 8 → reflex CBC" should fire when manual entry crosses the threshold, just as it does for simulator-emitted results (since both publish RESULT_RECEIVED). The publish path is identical, so the rules-runtime treatment should match — but I didn't seed a reflex rule and verify the cascade.
- **Verify-on-save → autoRelease rule** also untested. If a "release verified normal results" rule exists, it should fire from the manual entry's RESULT_VERIFIED publish. Same publish-shape argument, same verification gap.
- **Order completion via verify-on-save.** The lifecycle watcher subscribes to RESULT_VERIFIED and promotes the order to `completed` once all results are at least final. With only 1 of 3 tests verified in scenario G, no promotion was expected — and that's correct — but I didn't run a "verify all 3" path to confirm the cascade end-to-end.
- **`useEntities` filter-race fix** is scoped to `ResultsForSpecimen` only. The same closure-capture issue exists wherever a useEntities filter closes over an async-loaded value (e.g. patient drawer waiting on insurance, order drawer waiting on client). I did not audit the rest of the codebase for the pattern. A general fix would change `useEntities`'s deps array, which is a larger refactor.
- **No page-level entry point.** Manual entry is reachable only via the specimen drawer. A "+ Manual result" button on the Results page header (asking "specimen?" first) was considered and deferred — the drawer-anchored UX matches the natural workflow ("I'm looking at this specimen, I need to add a result").

**Decisions:**
- **Verify-on-save creates the result with `status: 'final'` directly** rather than creating-as-preliminary then routing through `lifecycle.transition('preliminary' → 'final')`. Rationale: it's a CREATE, not an UPDATE, so there's no transition guard to satisfy at insert time. Two writes (create then transition) would also produce two RESULT_RECEIVED publishes, which is wrong. Single-create + dual-publish (RESULT_RECEIVED + RESULT_VERIFIED) gives the correct event semantics.
- **Auto-flag from resolved range, not test default.** The form's old `flagFor(test, raw)` used `test.refRangeLow/High` directly. Now uses the demographic-resolved range. This means the flag a manual operator sees in the form mirrors what the simulator would produce for the same patient + value.
- **Range source pill (`matched` / `default`) is shown even when range bounds are present.** Operators benefit from knowing "did patient demographics match a specific range, or am I seeing the catalog-wide default?" — especially in pediatrics or sex-specific tests. No pill = no range available at all (e.g. culture).
- **Re-key on order.id rather than fix `useEntities`.** Two ways to plug the closure-capture race: (a) make `useEntities` accept a deps array (breaks call sites that pass inline filters every render → infinite reload), or (b) re-key the consuming component to remount when the captured value lands. Chose (b) — surgical, doesn't change the hook's contract. The general fix can come later.
- **Skipped the page-level "+ Manual result" entry point.** Adds two-step navigation (specimen picker, then form) where the drawer-anchored path is one step. If a real workflow demands it (e.g. tech receiving paper send-out reports who only has the patient name, not the specimen), revisit.

Switched to sequential `for await` execution — singleton config can only be tested sequentially anyway. This is not a real-world concern (a lab has one operator changing config at a time; rapid lab_config writes are not a real workflow), but it's worth noting that the cache + invalidation path is correct, the test harness was wrong.

**What I deliberately did NOT verify (honest gaps):**
- **Cross-tab cache race.** Two browser tabs of the LIS open simultaneously. Tab A toggles 1-2s off; Tab B's watcher cache holds the prior value for up to 1s. Within that window a QC write in Tab B fires 1-2s when it shouldn't. Mitigation already built — `db.subscribe` invalidates the cache — but `db.subscribe` is per-tab, so the second tab needs its own write event. In a single-tab prototype this isn't an issue; in production the cache TTL should be 0 (always re-read) or BroadcastChannel sync should be added.
- **Existing violations.** Disabling a rule does NOT retroactively clear violations the rule fired before being disabled. The help text notes this ("Existing violations are preserved — clear them via the Acknowledge button"), but I didn't write a regression test for it.
- **Re-enabling does NOT replay history.** A rule disabled while a 9-run chain was building, then re-enabled at run 10, will fire 10-x normally (since the watcher uses chronological history regardless of when it was previously disabled). This is the correct lab behavior — the rule treats history as physical reality, not as a function of policy at the time. But it means a lab that toggles rules around a marginal QC run can have unexpected fires later. Documented but not specifically tested.
- **`evaluateNow` re-evaluation path.** `westgardWatcher.evaluateNow(id)` re-runs the evaluator on a single QC result (used when correcting a value). It now goes through the same `__readDisabledRules` path so it'll reflect current config. Not specifically end-to-end tested.
- **`lab_config` isn't included in snapshot diff yet.** Backup/restore covers all collections including this one (verified by inspecting `COLLECTIONS`), but I did not run an export → wipe → import roundtrip to confirm the singleton survives intact.

**Decisions:**
- `lab_config` is a singleton (one row, fixed id `'lab_config'`) rather than a multi-row settings table. Future settings can land as additional fields on this row — keeps reads to a single `db.get('lab_config', 'lab_config')` instead of N rows. If we ever need per-lab settings in a multi-tenant build, this becomes a per-tenant row keyed by tenant id; the field shape stays.
- Disabled rules are global (lab-wide), not per-test or per-instrument. Per-test would invite operators to create configurations that are inconsistent across the analyte panel; per-instrument is rarely a real Westgard concern. If a lab actually needs per-test, that's a future field on the test record (`westgardRulesDisabled?: string[]`) overlaid on the lab default.
- The factory at the schema layer + the resolver at the runtime layer both filter non-string entries. Two-layer defense matches the per-test escalation thresholds pattern from earlier today — either layer alone could miss bad data after a snapshot import, so both is fine here.
- Watcher caches `qcDisabledRules` for 1s + invalidates on `lab_config` writes. Avoids a `db.get` on every QC write during a burst (e.g. importing a lot of historical QC at once); invalidation guarantees toggle-then-write sees the new value. The 1s window only matters if writes come from a different tab, which is documented as a single-tab prototype assumption.
- 1-2s is enabled by default (matching CLSI EP23 practice for new installations). The lab opts OUT, not in. Operator-friendly default.

| Case | Behavior | Verdict |

### User session — 2026-05-07 (evening, local) — Edge-case audit + three real fixes

**Tackled:** User asked for an edge-case shakedown. Ran a structured suite over mappers, HL7, reference ranges, Westgard, qcGate, lifecycle, labels — about 40 cases covering empty input, malformed input, boundary values, escape characters, missing demographics, idempotence, and security.

**Bugs caught and fixed:**
1. **`labels.renderHtml` had a real XSS** — interpolated `render.patientLine`, `render.mrn`, etc. directly into HTML and the modal mounted via `dangerouslySetInnerHTML`. A patient name like `<script>alert(1)</script>` would execute on modal open. Fixed by adding `__htmlEsc` (`& < > " '`) on every interpolated value. Verified by injecting `<script>window.__pwned=true</script>` and confirming the flag never gets set even after appending to live DOM.
2. **Reference range matcher accepted sex-constrained rows when patient sex was missing** — opposite of the existing DOB-defensive behavior. Now: a sex-constrained range only matches when patient.sex is known. A patient with no sex falls to the default range.
3. **`parseORM` silently fabricated `Date.now()` for `orderedAt`** when ORC-9 was empty. Replaced with the documented HL7 fallback chain: ORC-9 → MSH-7 → `null`. Never `Date.now()`.

**Verified non-issues (documented as expected behavior):**
- Empty/malformed CSV / JSON: graceful errors, no crash.
- HL7 escape sequences (`\F\`, `\S\`, `\R\`, `\T\`, `\E\`) round-trip correctly through build + parse.
- HL7 partial date (e.g. `198504` without day): yields empty `dob`, no crash.
- HL7 unknown sex code (`Z`): silently dropped to `''`, not preserved.
- Westgard boundary values: 1-2s/1-3s/2-2s/R-4s all use strict `>` (exactly-at-threshold does NOT trip).
- Westgard `sign(0)` = 0: a perfect z=0 reading correctly breaks "same-side" runs (4-1s, 10-x, 2-2s).
- QC gate: warn-severity violations don't lock; resolved violations don't lock; missing latest-QC means lock-clearing condition not met.
- Lifecycle: illegal transitions throw with the allowed-targets list; idempotent terminal states succeed without write; missing entity / unknown collection throw with descriptive errors.
- Labels: orphan specimen falls back to `— UNKNOWN PATIENT —`; specimen with no accession produces a label without barcode; non-existent id throws.

**Decisions:**
- Defensive policies on reference ranges (DOB-missing skips age-bounded; sex-missing skips sex-bounded) are now consistent — both follow the same rule.
- `parseORM` orderedAt fallback is documented in HL7 spec terms (ORC-9 → MSH-7) instead of a JS implementation default.
- HTML rendering of any user-supplied data MUST go through `__htmlEsc`; `dangerouslySetInnerHTML` without escaping is now an explicit ban.

**Cache version bumps:** `20260507y` → `z` → `aa` (three turns in this iteration, each with a verifiable fix).

| 2026-05-07 | **Cache-busting via `?v=YYYYMMDDx` query on every script tag** | Python http.server doesn't send no-cache headers. Versioned URLs ensure browser pulls fresh bytes on every reload during dev. Bump the constant in `index.html` after JS edits. |
| 2026-05-07 | **Per-test critical-escalation thresholds: defaults-on-misconfig, not repair** | Resolver in `critical-escalation.js` rejects null / NaN / Infinity / non-numeric / zero / negative / `T2 ≤ T1` and falls all the way back to global defaults (45s / 90s) with a `console.warn` naming the test. Repair (e.g. swapping T1↔T2 or clamping) would mask operator error; defaults-with-warning preserves observability. Per-instrument was also considered and rejected for the same reason. If a real lab needs per-test, that's a future field on the test record overlaid on the lab default; not built speculatively. |
| 2026-05-07 | **`lab_config` is a singleton collection (id='lab_config'), not a multi-row settings table** | One round-trip `db.get('lab_config', 'lab_config')` instead of N. Future installation-level fields land as additional keys on this row. If a multi-tenant build ever materializes, it becomes a per-tenant row keyed by tenant id; the field shape stays identical. |
| 2026-05-07 | **Manual verify-on-save creates the result with `status: 'final'` directly, not via `lifecycle.transition`** | Result entry is a CREATE, not an UPDATE — there's no transition guard to satisfy at insert time. Two-step (create-as-preliminary, then transition) would also produce two `RESULT_RECEIVED` publishes (wrong). Single-create with both `RESULT_RECEIVED` + `RESULT_VERIFIED` published gives correct event semantics: rules subscribed to received still cascade (critical-flag, reflex), and the lifecycle watcher promotes order completion via the verified event. |
| 2026-05-07 | **Re-key strategy for closure-captured async values in `useEntities` filters** | When a `useEntities` filter closes over an async-loaded value (e.g. `order` from `useEntity`), the filter is captured at first render with the value still null, and `useEntities` reload only re-fires on collection writes — not on filter-identity changes. Surgical fix: re-key the consuming component on the captured value's id (`<X key={order?.id} ... />`) so it remounts when the value lands. Avoids changing `useEntities`'s contract; doesn't break call sites that pass inline filters. The general fix (deps array on `useEntities`) is a future refactor. |
| 2026-05-07 | **Result corrections create a new record; the prior is never overwritten** | The prior result really WAS final at the time it was reported (often delivered to a client). Mutating its status erases that history and breaks audit. New record carries `correctionOf` → prior; prior gets a single back-reference stamp `supersededByResultId` (status stays `final`). Display-time filter hides superseded versions from the latest-only view; explicit toggle reveals the chain. This avoids the lifecycle ambiguity of "what's the correct status for a superseded final result?" — it's still final, just no longer the current report. |
| 2026-05-07 | **Auto-release a correction iff the prior was released; auto-verify by the issuing operator** | If the prior went to a client, the client must see the amendment — `delivery-watcher` re-fires `RESULT_RELEASED` on `RESULT_CORRECTED` so the existing channel chain runs. HL7 emits `OBX-11='C'` automatically because the corrected record has `status: 'corrected'`. If the prior was held internally, the corrected record waits for an explicit release. Verification is folded into the correction itself — the operator who issued the correction is signing off, no second verify pass. |
| 2026-05-07 | **Correction-chain panel walks by `(specimen, test)` membership, not strictly via `correctionOf` linked-list** | Membership-based walk is resilient to partially-malformed chains (e.g. an imported snapshot where a corrected record's back-reference target was never persisted). Chronological sort gives the same ordering as a clean linked-list walk in nearly every case. The data model still uses `correctionOf` as the canonical link; the UI is just charitable about reading it. |
| 2026-05-07 | **Correction reason is a required dropdown of CLIA-trackable categories + optional free-text comments** | Labs need to report correction rate by category (transcription error vs. wrong specimen vs. instrument drift, etc.) — a single free-text would land everything in "Other". 8 preset reasons cover the standard CLIA buckets; comments capture detail. Submit is gated until both value-changed AND reason-picked, so an operator can't fat-finger a no-op correction with no audit context. |
| 2026-05-08 | **`other-pages.jsx` split as a structural domain-page move, not a component-by-component refactor.** Codex extracted the 5,800-line junk drawer into 12 domain page files (shared / dashboard / order-workflow / result / interop / reports / reference / label / mapper / quality / notification / admin) without touching component boundaries or runtime contracts. | The runtime is browser globals via Babel-compiled bundle scripts — no ES modules, no import graph, no per-component encapsulation contract to honor. A finer-grained refactor (one component per file) would have introduced a boundary the project doesn't actually use yet, blurred the structural-only intent, and made verification (every component still renders) substantially harder. Domain-level grouping matches how the team already navigates the code (by page surface) and preserves behavior with the smallest possible diff per file. |

```typescript
interface AuditEvent {
  id: UUID;
  // Actor
  userId?:    UUID;       // null for system-generated events
  sessionId?: UUID;
  ipAddress?: string;
  userAgent?: string;
  // Subject
  eventType:    AuditEventType;
  resourceType: string;   // "Patient" | "Order" | "Specimen" | "Result" | ...
  resourceId:   UUID;
  // Change data — JSON snapshots for before/after comparison
  previousValue?: Record<string, unknown>;
  newValue?:      Record<string, unknown>;
  // Context
  reason?:    string;
  occurredAt: ISO8601;   // server-authoritative UTC; never accept client-supplied value
}

type AuditEventType =
  // Patient
  | "PATIENT_CREATED" | "PATIENT_UPDATED" | "PATIENT_MERGED" | "PATIENT_ACCESSED"
  // Order
  | "ORDER_CREATED" | "ORDER_UPDATED" | "ORDER_CANCELLED" | "ORDER_REJECTED"
  // Specimen
  | "SPECIMEN_ACCESSIONED" | "SPECIMEN_RECEIVED" | "SPECIMEN_REJECTED"
  | "SPECIMEN_PROCESSED"   | "SPECIMEN_DISPOSED"
  // Result
  | "RESULT_ENTERED" | "RESULT_VERIFIED" | "RESULT_REPORTED"
  | "RESULT_CORRECTED" | "RESULT_CANCELLED"
  // Critical values
  | "CRITICAL_VALUE_DETECTED"   | "CRITICAL_VALUE_NOTIFIED"
  | "CRITICAL_VALUE_ACKNOWLEDGED" | "CRITICAL_VALUE_ESCALATED"
  // QC
  | "QC_RUN_RECORDED" | "QC_RULE_VIOLATED" | "QC_LOCKOUT_APPLIED" | "QC_OVERRIDE"
  // User / session
  | "USER_LOGIN" | "USER_LOGOUT" | "USER_LOGIN_FAILED" | "USER_LOCKED"
  | "USER_CREATED" | "USER_UPDATED" | "USER_ROLE_CHANGED"
  // System / infrastructure
  | "RULE_APPLIED" | "INTERFACE_MESSAGE_RECEIVED" | "INTERFACE_MESSAGE_SENT"
  | "CONFIGURATION_CHANGED" | "LABEL_PRINTED";
```
